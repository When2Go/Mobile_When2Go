# pr-review

> 트리거: "PR 리뷰해줘", "PR #숫자 리뷰", "PR 코멘트 남겨줘", "이 PR 리뷰", "리뷰 코멘트 달아줘", "pr review"

`/review`(로컬 검사) 와 다른 스킬이다. 이 스킬은 **GitHub PR의 변경 라인에 직접 코멘트를 게시**한다. PR 머지 전 리뷰어 역할로 동작한다.

---

## 문체 규칙 (절대)

이 스킬이 생성하는 **모든 GitHub 텍스트**(라인 코멘트·리뷰 요약 본문)는 아래를 무조건 지킨다.

### 1. 음슴체 (해라체의 -ㅁ/-음 명사형)

- 종결은 `~음`, `~함`, `~됨`, `~임`, `~없음`, `~필요함` 형태
- 평서문 종결 `~다`, `~합니다`, `~입니다`, `~한다`, `~합니다`, `~됩니다` **전부 금지**
- 의문은 `~?` 또는 `~인지?` 정도만 허용

| 금지 | 허용 |
|---|---|
| "매직 넘버를 상수로 빼야 합니다." | "매직 넘버임. 상수로 빼야 함." |
| "타입이 any 입니다." | "any 임. 타입 명시 필요함." |
| "다크모드 분기가 누락되었습니다." | "다크모드 분기 빠짐." |
| "이 부분을 확인해주세요." | "확인 필요함." |
| "수정하면 좋을 것 같습니다." | "수정 필요함." |

### 2. 간결

- **라인 코멘트는 한 문장.** 최대 두 줄. 절대 단락 금지.
- 부연 설명·인사·맺음말 금지. 지적 그 자체만 쓴다.
- 줄 수가 늘어나는 순간 핵심이 흐려진다고 본다 → 한 줄로 안 되면 지적이 잘못 잡힌 것.

### 3. AI 말투 금지

아래 표현은 **단 한 번도** 등장하면 안 된다.

- "~할 수 있을 것 같습니다", "~하면 좋을 것 같습니다"
- "권장드립니다", "제안드립니다", "권유드립니다"
- "고려해보시면", "고려해볼 수 있습니다"
- "혹시 ~하시다면", "필요시"
- "확인 부탁드립니다", "검토 부탁드립니다"
- 이모지 (👍 ✨ 🚀 등) — 전부 금지
- 칭찬 멘트 ("좋은 접근입니다", "깔끔하네요") — 금지. 리뷰는 지적이 본질임

### 4. 라인 기반

- 코드에 대한 지적은 **반드시 해당 코드 라인에 라인 코멘트로 게시.**
- 전체 PR 단위 코멘트(`gh pr comment`)는 **요약 한 줄만** 허용. 라인에 붙일 수 있는 지적을 본문에 적지 않음.

## 워크플로우

### 1. PR 식별

```bash
# 인자에 번호 있으면 그대로
PR=42

# 없으면 현재 브랜치의 PR
PR=$(gh pr view --json number -q .number)
```

PR 못 찾으면 "현재 브랜치에 열린 PR 없음. PR 번호 명시 필요함." 한 줄로 사용자에게 반환하고 종료.

### 2. 변경 분석

```bash
gh pr view $PR --json title,body,headRefName,baseRefName,files
gh pr diff $PR
```

`headRefName`을 로컬에 체크아웃해 실제 파일을 읽는다. diff 만으로는 컨텍스트가 부족함.

```bash
git fetch origin
git checkout $(gh pr view $PR --json headRefName -q .headRefName)
```

### 3. 리뷰 분석 — when2go-qa spawn

`Agent` 툴로 `when2go-qa` 서브에이전트를 **새 컨텍스트**로 spawn 한다. 전달 정보:

- PR 번호, head 브랜치, base 브랜치
- 변경 파일 목록 (`gh pr view $PR --json files -q '.files[].path'`)
- `.claude/commands/review.md` 체크리스트 (Hook 통과·코드 품질·디자인 시스템·반복 패턴·테스트)
- **출력 포맷 강제** — 아래 JSON 스키마로만 반환하라고 지시:

```json
{
  "summary": "한 줄 요약 (음슴체)",
  "comments": [
    {
      "path": "src/components/Foo.tsx",
      "line": 42,
      "side": "RIGHT",
      "severity": "CRITICAL|WARNING|INFO",
      "body": "한 문장 지적 (음슴체)"
    }
  ]
}
```

`side` 는 추가/변경된 라인이면 `RIGHT`, 삭제된 라인이면 `LEFT`. 멀티라인은 `start_line` + `line` 사용.

### 4. 문체 변환 검증

QA 가 반환한 `body` 들을 **메인 에이전트가 한 번 더 정제**한다. QA 가 합쇼체로 적은 경우가 흔하니 무조건 음슴체로 변환:

| 패턴 | 변환 |
|---|---|
| `~합니다` 종결 | `~함` |
| `~됩니다` 종결 | `~됨` |
| `~입니다` 종결 | `~임` |
| `~필요합니다` | `~필요함` |
| `~누락되었습니다` | `~누락됨` 또는 `~빠짐` |
| `~확인해주세요` | `~확인 필요함` |
| `~제안드립니다` | (제거하고 지적만 남김) |

이모지·칭찬·인사·맺음말은 발견 즉시 제거.

문장이 두 줄 넘어가면 **다시 한 줄로 압축**. 안 되면 그 지적은 두 개로 쪼개 각 라인에 따로 단다.

### 5. 라인 코멘트 게시

여러 코멘트는 묶어서 **하나의 review** 로 보낸다. 각 코멘트를 따로 POST 하지 않음 (PR에 알림이 N번 가서 노이즈가 됨).

```bash
# review.json 작성
cat > /tmp/pr-review-$PR.json <<EOF
{
  "event": "COMMENT",
  "body": "{summary 음슴체 한 줄}",
  "comments": [
    {"path": "src/...", "line": 42, "side": "RIGHT", "body": "매직 넘버임. 상수로 빼야 함."},
    {"path": "src/...", "line": 88, "side": "RIGHT", "body": "any 임. 타입 명시 필요함."}
  ]
}
EOF

gh api repos/{owner}/{repo}/pulls/$PR/reviews \
  -X POST \
  --input /tmp/pr-review-$PR.json
```

`event` 값:

- `COMMENT` — 기본. 머지 가부 판단 보류.
- `REQUEST_CHANGES` — CRITICAL 1건 이상일 때만.
- `APPROVE` — 이 스킬은 자동 approve 안 함. 사용자가 명시적으로 "approve도 같이"라고 했을 때만.

### 6. 결과 보고

게시 후 사용자에게 한 줄로만 답한다.

```
PR #42 리뷰 게시함. 라인 코멘트 N건 (CRITICAL n / WARNING n / INFO n).
```

링크는 `gh pr view $PR --json url -q .url` 로 받아 같이 출력.

```
```
any 임. unknown + 타입 가드 또는 명시적 타입 필요함.
```
```
하드코딩 색상값. NativeWind 토큰으로 교체 필요함.
```

```
```

```

### 나쁜 예 (전부 위반)

```
이 부분은 매직 넘버를 사용하고 있어서 상수로 빼주시면 좋을 것 같습니다 👍

```
```
타입이 any로 되어 있는데, unknown 타입과 타입 가드를 사용하시거나, 명시적인 타입을 정의하는 것을 권장드립니다.
→ 위반: 합쇼체, "권장드립니다", 한 줄로 압축 가능한데 풀어씀
```

## 범위·제약

- **백엔드 레포 PR 거부** — 본 스킬은 프론트엔드 레포 전용. 백엔드 PR 요청이면 "별도 레포임. 백엔드는 대상 아님." 한 줄로 종료.
- **승인 자동화 금지** — `APPROVE` event 는 사용자가 명시 요청했을 때만.
- **머지 자동화 금지** — 이 스킬은 코멘트까지만. `gh pr merge` 절대 호출 안 함.
- **테스트 미실행 PR 차단** — `gh pr checks $PR` 로 테스트 실패면 라인 코멘트 게시 후 요약에 "테스트 실패. 우선 해결 필요함." 추가.
- 같은 PR 에 이미 리뷰가 있으면 새 리뷰로 또 게시함. **이전 리뷰는 삭제하지 않는다** (히스토리 유지).
