# PR 본문 작성 가이드

> 모든 PR 본문은 **비전문가도 한 번 읽고 무슨 변경인지 이해할 수 있는 수준**으로 쓴다.
> 적용 대상: 사람이 직접 쓰는 PR, `github-issue-work` 스킬이 자동 생성하는 PR 모두.

---

## 문체 (필수)

PR·이슈 본문의 평서문은 **"~습니다" 체(합쇼체)** 로 작성합니다. "~다/~한다" 체 금지.
이슈 코멘트도 동일합니다.

- 적용: 한 줄 요약·변경 설명·리뷰어 참고 등 문장 형태 전부.
- 예외: `[Feature] …` 제목, 표·코드블록·명령어, 명사구 섹션 헤더는 그대로 둡니다.

---

## 원칙

1. **한 줄 요약을 가장 먼저**. 이 PR을 한 마디로 표현하면? 부터 시작.
2. **무엇을 / 왜 / 어떻게 쓰는지** 순서로. 라이브러리 이름 나열이 아니라 실제 동작 위주.
3. **고유명사·기술 용어는 풀어 쓰기**. 어쩔 수 없는 핵심 용어(예: NativeWind, BottomSheet)만 남기고, 그조차 한 줄 풀이를 옆에 붙인다.
4. **표·체크박스로 한눈에 보이게**. 자동 리뷰 결과, 테스트 체크리스트는 표로.
5. **직접 확인하는 법 섹션 필수**. 리뷰어가 앱에서 무엇을 확인할지 체크 항목으로만 적습니다. **`npm install` / `npx expo start` / `npm test` 같은 범용 실행 명령 블록은 항상 제외합니다** (누구나 아는 보일러플레이트라 노이즈). 이 변경에서만 필요한 특수 명령이 있을 때만 그 명령을 적습니다.
6. **리뷰어 참고는 마지막에**. 머지 후 영향 범위, 의도적으로 건드리지 않은 영역 등.

---

## 안 좋은 예 vs 좋은 예

### ❌ 안 좋은 예 (라이브러리 나열 + 기술 용어 폭격)

```
- NativeWind v4 + tailwindcss 3.4 셋업 (babel/metro/tailwind config)
- ThemeContext: system/light/dark 3-mode + nativewind colorScheme 동기화
- MobileLayout (children pattern): 헤더 + 바텀탭 + 다크모드
- BottomSheetModal: @gorhom/bottom-sheet 래퍼
```

→ 무엇을 쓰는지는 적혀 있지만, **왜 필요한지·어떻게 쓰는지**가 없고 비전문가는 한 줄도 이해 못 한다.

### ✅ 좋은 예 (목적 + 사용법)

```
### 1. 스타일을 쓸 수 있게 셋업 (NativeWind)
- 지금까지는 RN의 style={{ ... }}로만 스타일을 줄 수 있었는데, 이제 웹처럼
  className="bg-blue-600 text-white" 같이 쓸 수 있습니다.
- 필요한 설정 파일을 다 만들었습니다.

### 5. 바텀시트 (BottomSheetModal)
- 아래에서 슥 올라오는 시트입니다. 외부 라이브러리를 직접 쓰지 않고 우리 래퍼만 쓰도록 통일했습니다.
- 사용법: <BottomSheetModal isOpen={...} onClose={...} title="...">
```

→ 무엇을 / 왜 / 어떻게 쓰는지가 한 묶음.

## 권장 본문 구조

```markdown
## 관련 이슈
closes #N

## 한 줄 요약
이 PR이 무엇을 하는지를 한 문장으로.

## 무엇이 바뀌었나
### 1. {평이한 한국어 제목} ({필요시 핵심 용어})
- 무엇: ...
- 왜: ... (생략 가능 — 의도가 자명하면)
- 어떻게 쓰는지: 코드 한 줄 예시 또는 사용 시나리오

### 2. ...

## 직접 확인하는 법
<!-- npm install / npx expo start / npm test 같은 범용 명령 블록 금지. 체크 항목만. -->
- [ ] 확인 항목 1 (앱에서 무엇을 보고 무엇이 맞아야 하는지)
- [ ] 확인 항목 2

## 자동 검사 결과 (when2go-qa)
| 검사 항목 | 결과 |
|---|---|
| 1. 타입·린트 에러 | ✅ 통과 |
| 2. 코드 품질 | ✅ 위반 0건 |
| 3. 디자인 시스템 | ✅ 위반 0건 |
| ... | ... |

## 리뷰어 참고
- 의도적으로 건드리지 않은 영역
- 머지 후 영향 범위
- exec-plan 정리 시점
```

---

## 자동 리뷰 결과 첨부 규칙

- **반드시 표로 정리**. 카테고리별 ✅/❌ 한 줄.
- **`[CRITICAL]/[WARNING]/[INFO] 건수 — 머지 가능` 같은 판정 한 줄은 쓰지 않습니다.** (PR 본문 금지)
- **`### INFO 상세` 섹션을 PR 본문에 넣지 않습니다.** INFO 항목은 PR에 싣는 대신, 작업을 수행한 사용자에게 "이 INFO 작업을 추가로 할지" 만 물어봅니다 (그 작업을 할지/말지 외 다른 건 묻지 않음). 사용자가 하기로 하면 작업에 포함, 안 하기로 하면 그대로 머지 진행.

---

## 톤 체크리스트 (PR 작성 후 자가 점검)

- [ ] 평서문이 전부 "~습니다" 체다 ("~다/~한다" 체 잔재 없음)
- [ ] 한 줄 요약을 읽고 동료가 \"아, 이런 작업이구나\"라고 이해할 수 있다
- [ ] 변경 사항에서 **라이브러리 이름 나열만 있는 줄**이 없다 (있다면 한 줄 설명 추가)
- [ ] 직접 확인하는 법이 있다
- [ ] 자동 리뷰 결과가 표로 정리돼 있다
- [ ] 비기술자 동료가 읽어도 50% 이상은 이해할 수 있다
